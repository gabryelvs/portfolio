1The problem

Moving money between two accounts looks like one UPDATE. It isn't. Two transfers at the same moment can both read the same balance and both spend it. A client that times out and retries can pay twice. A float can lose a penny, and a bug can create money out of nothing. PayLedger is a small payments API built to get those four things right: users hold wallets in several currencies, move money between them, and every movement is written to an append-only double-entry ledger.

2Constraints

  • Money is an integer. Amounts are stored in minor units as BIGINT; floats never touch a balance.
  • Every transaction balances. Its signed entries sum to zero per currency, checked before anything is written.
  • No overdraft, even under concurrent load.
  • Retries are safe. The same key and body return the same result; the same key with a different body is a conflict.
  • Only the owner moves money. A wallet that isn't yours doesn't exist, as far as the API is concerned. pending fix
ledger.pyassert_balanced() sums entries per currency and rejects anything non-zero.

3Architecture

A FastAPI app with a thin router layer over a service layer, backed by PostgreSQL and migrated with Alembic. Seven tables: users, accounts, wallets (holding a cached balance_minor), transactions, ledger entries, idempotency keys, and webhook events. The diagram above is the whole transfer path; everything that matters happens inside one database transaction, so there is no state where money has left one wallet and not arrived in the other.

4Hard problems

Two transfers, one balance

The failure is a lost update: two requests read a balance of 100, both decide 100 is available, and both debit it. Postgres's default isolation, READ COMMITTED, doesn't stop that on its own. The fix is to lock the rows being changed: both wallets are read with SELECT … FOR UPDATE, and the balance is checked only after the locks are held. Locking two rows invites a deadlock when two opposite transfers each grab one, so the wallets are always locked in ascending id order.

transfer_service.py_lock_wallet() and the sorted lock order, lines 28–53.
# Lock wallet rows in a deterministic order to avoid deadlocks.
first, second = sorted([from_wallet_id, to_wallet_id])
locked = {first: _lock_wallet(db, first), second: _lock_wallet(db, second)}
src, dst = locked[from_wallet_id], locked[to_wallet_id]

if src.balance_minor < amount_minor:
    raise InsufficientFunds()

The proof is a test that fires 20 threads at a wallet holding exactly 1,000, each sending 100. Exactly ten succeed, the source never goes below zero, and the total across both wallets is unchanged.

testtest_no_lost_updates_under_concurrency

A retry that pays twice

Clients send an Idempotency-Key; a replay with the same key and body returns the original response, and the same key with a different body is rejected with a 409. The first version checked the key, ran the transfer, and stored the key in a separate commit. That was fine for one retry at a time, but two simultaneous retries could both transfer. The key is now claimed inside the same transaction as the transfer, so they commit or roll back together. pending fix

testconcurrent same-key requests: exactly one transfer, no 500s pending

A wallet that isn't yours

While writing this page I audited the API and found that a transfer never checked who owned the source wallet: any signed-in user could move money out of anyone's. Every wallet, transfer and transaction route now checks ownership and answers 404 for anything that isn't yours, so the API doesn't even confirm it exists. pending fix

5How it's tested

Every test runs against a real PostgreSQL, with the schema dropped and recreated per test, because the bugs that matter here only exist in a real database. Unit tests cover the money and ledger rules; service tests cover transfers and idempotency; API tests go through HTTP; one concurrency test proves the locking. CI runs the linter and the full suite against Postgres 16 on every push.

ci.ymlruff + pytest, Postgres 16 service container.

6What I'd change

  • The ledger's balance rule lives in application code. A deferred constraint trigger in Postgres would make an unbalanced transaction impossible, not just unlikely.
  • Each wallet keeps a cached balance that nothing reconciles against the ledger. A scheduled check would catch drift.
  • The concurrency test only sends money one way, so the deadlock-avoiding lock order is reasoned about, not exercised.
  • Webhook events are recorded but never sent. Webhook-Dispatcher is the missing half.
